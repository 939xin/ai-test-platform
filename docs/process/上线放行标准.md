# 上线放行标准

> 用途：**一个人**判断「这个产品能不能上线」时，按这份标准取证、签字、留档。
> 不是给团队用的流程文件，是给自己用来**对抗「解释一下就放行」这种冲动**的。
>
> 配套工具：本平台（功能回归 + 证据留档）+ k6（性能容量，见 `tools/k6/`）。
> 版本：v1（2026-10-22）

---

## 0. 这份标准管什么

| 管 | 不管 |
|---|---|
| 功能回归是否达标（自动化用例） | 界面审美、交互体验 |
| 容量与稳定性是否达标（k6 压测） | 安全渗透测试 |
| 缺陷是否构成上线阻塞 | 兼容性矩阵（多浏览器 / 多机型） |
| 证据是否可追溯（挂到具体版本） | 上线部署操作本身 |

**前提**：你测的是**别人的产品**，结论要以书面形式交给对方或上级。所以每一条判据都必须能被第二个人复核。

---

## 1. 三条原则

1. **可复现**：任何一项「通过」，都要能说出是哪一次执行、哪个版本、什么参数。
2. **可辩护**：数字要经得起追问「你怎么测的」。测不准的，宁可写「未验证」，不写「没问题」。
3. **有标准**：**先定放行标准，再开始测**。测完再定标准的，一定会把标准定成结果的样子。

---

## 2. 必过项（Gate）

七条，**缺一条就是「不通过」**。没有「差不多」这一档。

| 编号 | 判据 | 取证方式 | 不满足 |
|---|---|---|---|
| **G1** | 门禁用例集 **100% 通过** | 平台：打 `gate` 标签的用例 → 按标签筛选 → 建计划执行 → 报告留档 | 不通过 |
| **G2** | 核心业务用例通过率 **≥ 98%**，且每个失败项都有一句书面结论（真 bug / 环境 / 已知问题） | 平台执行记录 + 缺陷单 | 不通过 |
| **G3** | **无未关闭的 P0 / P1 缺陷** | 平台缺陷表按优先级筛 | 不通过（P2 可豁免，见 §4） |
| **G4** | 性能：目标 RPS 下 `p95 < 阈值` 且 `http_req_failed < 0.1%` | k6 报告 + 阈值判定 | 不通过 |
| **G5** | 稳定性：**连续 30 分钟**压测，内存 / 连接数无持续增长趋势 | k6 长跑 + 服务端监控截图 | 不通过 |
| **G6** | 所有证据挂在**同一个 `release_tag`** 下（执行记录 + 报告 + k6 摘要） | 平台执行记录的 `release_tag` 字段 | 不通过 |
| **G7** | 回滚方案已写在放行记录里，且**被验证人知道怎么回滚** | §6 记录表 | 不通过 |

> `release_tag` 字段来自功能单 **F1-7**。F1-7 没做完之前，G6 用「报告文件名 + 手写记录」临时顶：把 tag 写进报告文件名的备注里，别偷懒跳过。

### 关于 G4 的「目标 RPS」怎么来

**不要拍脑袋。** 按下面顺序推：

1. 找真实流量数据：线上/测试环境的日均 PV、峰值时段 PV、峰值系数（一般 3–5 倍）
2. 换算并发：`并发 ≈ 目标 RPS × 平均响应时间(秒)`
   例：目标 100 RPS、平均响应 200ms → 需要约 20 并发
3. 如果拿不到真实数据，就用「服务端资源水位」反推：CPU 到 70% 时的 RPS 即为该环境容量上限，再打 70% 折作为目标

拿不到 1 和 2 的时候，**必须把「负载模型来自假设」写进放行记录**。这一句比数字本身重要。

## 3. 执行流程（六步）

```
① 定标准        写下本次的 release_tag、目标 RPS、p95 阈值、必跑用例范围
② 跑功能        平台：门禁计划 + 核心链路计划，全部执行记录都带同一个 release_tag
③ 逐条解释      红项不许"看着没问题"放过，每条写一句结论，真 bug 进缺陷表
④ 跑性能        k6：先 1 VU 验证脚本（见 tools/k6/README.md），再逐级加压，再 30 分钟稳定性
⑤ 填放行记录    §6 的表格，逐条打勾/打叉，写结论
⑥ 归档          报告 + k6 摘要 + 放行记录，按 release_tag 放一起
```

第 ③ 步是最容易糊弄自己的一步。规则：**解释不了的，就不能算通过**。你说不清为什么红，就说明你没搞清这条链路。

---

## 4. 结论只有三档

| 结论 | 条件 | 后续 |
|---|---|---|
| **通过** | G1–G7 全绿 | 可以上线 |
| **有条件通过** | G1–G7 中只有 **G3 的 P2 缺陷**或 **G2 的单项失败**，且：写明影响范围 + 对方书面接受 + 给出下次修复版本 | 上线，并把豁免项写进记录 |
| **不通过** | 其余任何情况 | 修完重测，**重测要从第 ② 步重跑**，不能只重跑红的那几条 |

「有条件通过」不是灰色地带，它有明确门槛：**影响范围写不出来、对方不接受，就退回不通过。**

---

## 5. 自我放行的六种借口（出现即停下）

| 借口 | 为什么不能接受 |
|---|---|
| 「这个红是环境问题」 | 那就在干净环境重跑一次证明它。没重跑就说环境问题，等于没测 |
| 「上次跑过了，这次代码差不多」 | 差不多就是没测。要么跑，要么写「未覆盖」 |
| 「P95 有点高，但用户应该感觉不到」 | 阈值是第 ① 步定的。事后放宽阈值 = 改卷子 |
| 「性能数据是我本机压的」 | 单机客户端先饱和时，你测的是自己的机器（本次平台的 perf 模块就是这个局限，见 §7） |
| 「这个缺陷影响不大，先上再说」 | P0/P1 一律阻塞。觉得不大，就把它降级并写理由，别口头放过 |
| 「只重跑失败的那几条就够了」 | 回归的意义是证明**整体**没坏。只跑红的，等于只检查没红的地方 |

## 6. 放行记录（每次发布填一份）

复制下面这段，填完存到报告目录，文件名建议 `release_{tag}_{日期}.md`。

```markdown
# 上线放行记录 · {产品名} {release_tag}

- 日期：YYYY-MM-DD
- 被测环境：{域名 / 地址}（{独立环境? 与生产同规格?}）
- 测试执行人：{你}
- 不可测项（如有）：{写明为什么没测}

## 功能

| 项 | 结果 | 证据 |
|---|---|---|
| G1 门禁 100% | ✅ / ❌ | 计划执行 id / 通过率 |
| G2 核心 ≥98%，失败已解释 | ✅ / ❌ | 失败项：{用例名 → 结论} |
| G3 无未关闭 P0/P1 | ✅ / ❌ | 缺陷 id 清单 |

## 性能（k6）

| 项 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 目标 RPS | {N} | {实测} | ✅ / ❌ |
| p95 延迟 | < {X} ms | {实测} ms | ✅ / ❌ |
| 错误率 | < 0.1% | {实测}% | ✅ / ❌ |
| 负载模型来源 | — | {真实数据 / 假设} | — |
| 客户端与被测机 | 分离 | {是否分离} | — |

## 稳定性

| 项 | 结果 | 证据 |
|---|---|---|
| G5 30 分钟无内存/连接增长 | ✅ / ❌ | {监控截图或数据} |

## 结论

- 判定：**通过 / 有条件通过 / 不通过**
- 若「有条件通过」，豁免项与对方确认方式：{写清楚}
- 回滚方案（G7）：{怎么做，谁执行，回滚后怎么确认}
```

## 7. 平台与工具的边界（别用错）

| 事项 | 用什么 | 说明 |
|---|---|---|
| 功能回归、门禁用例 | ✅ 本平台 | 接口 + Web UI + 场景 + 计划，够了 |
| 功能执行前后对比 | ✅ 本平台 | 同一用例两次执行结果对比 |
| 性能容量结论 | ❌ 本平台 perf 模块 | 只能压单接口、客户端是本机、最长 10 分钟 → 不能作为放行依据 |
| 性能容量结论 | ✅ k6（`tools/k6/`） | 链路脚本、阶段加压、多机可扩展 |
| 单接口改前改后对比 | ✅ 本平台 perf 模块 | 「加索引前后 p95 变化」这类相对对比，它是有效的 |
| 证据归档 | ✅ 本平台报告页 | 报告 + 截图 + 执行记录，但**必须带 release_tag** |

> 平台 perf 模块的正确用法：**证明「改动有没有让这个接口变慢」，不证明「系统能扛多少」。**

---

## 8. 别在这份标准上偷的懒

- 标准可以改，但**改必须留痕**（写清哪天、为什么、改了什么），并且**不能在测完之后改**
- 阈值可以松弛，但松弛的理由要写在记录里（例如「首版无真实流量数据，按 CPU 70% 反推」）
- 没有一项「通过」是靠记忆得出的。**记忆不是证据。**
