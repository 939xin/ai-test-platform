### P0-1 · 断言期望值非法时降级，不再 500

**状态：✅ 已完成（2026-10-22）** —— 两个数值分支各自 try/except，附录 A 的片段现在输出两行 `passed: False`，无 RAISED。

**现象**：用户在断言里把期望值填成 `abc`（或 `200ms` 这种带单位的串），整个执行接口报 500。

**证据（已实测，见附录 A）**

- `backend/app/services/assertion_engine.py:23` —— `expected_int = int(expected)` 裸调用
- `backend/app/services/assertion_engine.py:34` —— `expected_float = float(expected)` 裸调用
- 异常从 `backend/app/services/api_executor.py:179` 的 `evaluate(...)` 一路抛出，
  调用方没有任何 try

**根因**：断言引擎假设「期望值一定是数字」，但这个字段是用户自由输入的字符串。

**改动要求**

1. `assertion_engine.evaluate()` 的两个数值分支各自包 `try/except (ValueError, TypeError)`，
   捕获后**返回一条失败断言**，不是抛异常：
   ```python
   return {
       "passed": False,
       "message": f"断言配置有误：期望值 {expected!r} 不是合法数字，请检查用例的断言条件",
       "actual": str(actual),
   }
   ```
2. `eq` / `ne` / `lt` / `gt` 的**语义一律不变**，只加容错。
3. `response_body` 分支的 JSONPath 解析失败已经返回 `passed=False`，保持现状不动。
4. 在函数 docstring 里补一句：期望值解析失败按「断言失败」处理，不按「执行错误」。

**验收（必须有测试）**

- `tests/test_assertion_engine.py` 新增用例：`expected="abc"` 于 `status_code` →
  `passed is False`，`"不是合法数字" in message`，**不抛异常**；`response_time` 同理。
- `verify_all.py` 全绿（说明原行为未变）。

**不要做**：不要把整条用例判成 `error`——这是**断言没通过**，不是**执行失败**，
两者的语义在执行中心要能区分开。

### P0-2 · 执行记录必达终态（三条链路）+ 启动清扫

**状态：✅ 已完成（2026-10-22）**

落地口径：接口**照常返回 200**，异常落成一条 `status=error` 的执行记录（`error_msg` 写
`执行器异常: 类型: 消息`）；选 200 而不是 500，是因为执行记录已经落库，前端需要在执行详情里
看到这条记录和失败原因，返 500 会让人以为"压根没执行"。

多覆盖了一条链路：`run-data-driven` 的逐行循环也在 `execute_case` 外层加了同样的保护
（同一文件、同一个缺陷，漏了它数据驱动照样会卡在 running）。

**现象 A**：任何未捕获异常都会让 `execution.status` **永远停在 `running`**。

**证据**

- `backend/app/api/executions.py:119-136`：先 `commit` 一条 `status="running"`，再执行，
  再回写终态。中间**没有 try/except/finally**。
- `backend/app/api/plans.py:205-253`：`_run_one()` 同样没有保护。一条用例抛异常 → 整个计划中断，
  后面的用例根本不会跑，且留下一条 running。
- `backend/app/services/scenario_runner.py:43`：`execute_case(...)` 没有保护。异常会穿透
  `run_scenario` → `scenarios.py:218` → 500。**最严重**：前面的步骤真的执行了，
  但 `scenarios.py:230` 的落库循环根本没走到，一条记录都没有。

**现象 B**：进程崩溃/重启后，所有 `running` 记录永远不结束（压测模块有 `reap_stale_runs()`，
功能执行没有对应机制）。

**改动要求**

1. **单条接口执行**（`executions.py` 的 `run_case`）：`execute_case(...)` 包
   `try/except Exception`，异常时构造一个与正常返回同骨架的结果：
   ```python
   result = {"status": "error", "duration_ms": int(...), "request": {}, "response": {},
             "assertions": [], "extracted": {}, "extract_errors": [],
             "error_msg": f"执行器异常: {type(e).__name__}: {str(e)[:150]}"}
   ```
   然后**照常走回写**（`end_time` / `duration_ms` / `result_json` 一个都不能少）。
2. **单条 Web 执行**（`run_web_case`）：同样处理，包在 `web_executor.execute_case(...)` 外层，
   注意 `web_session.finish_case` 仍然要执行（它内部已有保护）。
3. **计划执行**（`plans._run_one`）：把「执行 + 回写」整段包起来，异常**只让这一条变成 error**，
   继续跑下一条——这与该函数现有 docstring 声明的「不因为某条用例自身的问题中止整批」一致。
4. **场景执行**（`scenario_runner.run_scenario`）：对**每个 step** 的 `execute_case(...)` 包
   try/except，异常→该步 `status="error"`，并**照常按 `fail_strategy` 决定是否继续**。
   这样 `scenarios.py` 的落库循环总能拿到全部步骤。
5. **启动清扫**：在 `backend/app/main.py` 的 `lifespan` 里，紧跟 `perf_run_manager.reap_stale_runs()`
   之后加一次 `reap_stale_executions()`（建议新建 `backend/app/services/execution_reaper.py`）：
   把 `status="running"` 且 `start_time` 早于 `settings.execution_stale_minutes`（新增，
   默认 60）的记录批量 UPDATE 成 `status="error"`，
   `result_json` 追加 `error_msg="进程重启或执行超时，本次执行未完成"`。
   用单条 `UPDATE ... WHERE` 完成，**不要逐行查、不要起线程**。
6. `config.py` 新增 `execution_stale_minutes: int = 60`。

**验收**

- 新增 `tests/test_execution_terminal_state.py`：`monkeypatch` 把
  `app.api.executions.execute_case` 换成 `raise RuntimeError`，用 `TestClient` 调
  `POST /api/cases/{id}/run`，断言：接口返回 500（或 200+error，二选一但要在卡里写明），
  **且库里那条记录 `status == "error"`、`end_time is not None`**。
- `reap_stale_executions()` 的测试：手工插一条 `running` + `start_time` 在 2 小时前，
  调用函数后断言其变成 `error`。
- `verify_all.py` 全绿。

**不要做**：不要在请求线程里起后台任务做这件事；不要改动 `perf_run_manager` 的既有逻辑。

### P0-3 · 报告 HTML 全量转义

**状态：✅ 已完成（2026-10-22）** —— 新增 `_esc()`，报告里所有来自用例/响应/项目名的插值均过它；
`tests/test_report_generator.py` 新增 5 项断言（含 `<script>` / `onerror` / 截图 src）。

**现象**：报告里有存储型 XSS，且响应体里的 `</pre>` 一类文本会把版面打乱。
报告页路由 `GET /api/reports/{filename}` 是**免鉴权**的（`reports.public_router`），
所以这条不能靠「反正是内部页面」带过。

**证据**

- `backend/app/services/report_generator.py:137-207`：`details_html += f"""..."""` 十余处裸插值，
  插入的变量包括 `step_description`、`message`、`request_url`、`request_headers`、
  `request_body`、`response_body`、`expected_value`、`actual_value`、`case_name`。
- 全文件 `html.escape` 出现次数为 **0**（已 grep 确认）。

**改动要求**

1. 文件顶部 `import html`，新增私有函数：
   ```python
   def _esc(value) -> str:
       """报告里的所有插值都走这里。报告会被浏览器直接打开，未转义等于允许被测接口往页面里注入 HTML。"""
       return html.escape("" if value is None else str(value), quote=True)
   ```
2. **把所有插值点**改成 `_esc(...)`。包括 `<pre>` 里的内容——`<pre>` 本身就保留换行，
   所以只需 escape，**不要**把 `\n` 换成 `<br>`。
3. `screenshots` 的 `src` / `href` 也要 escape（虽然是系统生成的相对路径，防御性处理）。
4. `stats` 里进 `<title>` 的 `generated_at`、`project_name` 同样处理。
5. 给 `_build_html()` 的 docstring 补一句：**任何新增插值都必须过 `_esc()`**。

**验收**

- `tests/test_report_generator.py` 新增：
  - 传入 `response_body='</pre><script>alert(1)</script>'` → 输出**包含** `&lt;script&gt;`，

  - 传入断言 `message='<img src=x onerror=alert(1)>'` → 同样被转义。
  - 传入中文/多行文本 → 转义后仍可读（`&quot;` 等不影响中文）。

### P0-4 · 前端长任务超时统一

**状态：✅ 已完成（2026-10-22）** —— 新增 `frontend/src/api/timeouts.js`（三个常量），

### P1-1 · 浏览器实例并发上限

**状态：✅ 已完成（2026-10-22）**

实际情况：`web_executor` 里**原本有一个** `threading.Semaphore(2)`，但它是硬编码的、
acquire 不带超时（第三个请求会无限阻塞请求线程）、也没有对外暴露。本次改成：
配置项 `web_max_concurrent_sessions`（默认 2）+ `web_browser_wait_seconds`（默认 30 秒排队），
`BoundedSemaphore` + 超时 acquire，超限返回 `status=error` 且 `error_msg` 说明当前上限；

名额满时禁用按钮并提示。释放放在原 `finally` 里，异常路径也一定会还配额。

**现象**：没有任何地方限制同时开几个 Chrome。两个人同时点执行 = 两个浏览器进程，
机器资源不受控。

**改动**

1. `config.py` 新增 `web_max_concurrent_sessions: int = 2`。
2. 在 `services/browser_manager.py`（或 `web_executor.execute_case` 外层）加
   `threading.BoundedSemaphore`，**拿不到就用带超时的 acquire**，超时返回一条
   `status="error"` + `error_msg="当前已有 N 个浏览器在执行，请稍后重试"` 的结果——
   与「浏览器起不来」的既有风格一致（`executions.py:151-156` 的注释写明了这条约定）。
3. `GET /api/web/status` 增加 `active_sessions` / `max_sessions` 两个字段，前端
   `RunCaseDialog` 在超限时禁用按钮并提示。

**验收**：并发发 3 次 `run-web`，第 3 次返回超限错误而非崩溃；3 次都结束后
`/web/status` 的 `active_sessions` 回到 0。

### P1-4 · 响应体入库上限

**状态：✅ 已完成（2026-10-22）** —— `response_body_max_chars`（默认 20 万字符）统一约束

### 4.2 D5 的技术依据（别推翻，除非改设计）

报告 HTML 里引用截图用的是**相对路径**（`screenshots/execution_12/step_01_x.png`，
见 `report_generator.py` 截图那段注释）。经 `/api/reports/report_xxx.html` 打开时，
浏览器把它解析成 `/api/reports/screenshots/...`。

- 若给 HTML 加 `?sig=xxx`：图片 URL **不会**自动带上 sig → **整份报告的图全裂**。
- 要修就得在生成时把 sig 烧进 HTML，于是 sig 有了过期时间，**老报告在过期后图全裂**。
- 且 `verify_all.py` 有 5 处直接 GET `/reports/{name}`（含两条 `..%2F` 越界测试），
  加签名会全部打破，而约束 C7 不允许为了让测试过而改弱断言。

**结论**：保留免鉴权，用「不可枚举」防枚举（当前文件名
`report_{type}_p{pid}_{tag}_{ts}` 完全可推导：项目 id + 执行 id + 秒级时间戳）。
若将来真上公网，正确做法是「报告与截图统一带签名，且截图改用绝对 URL」——那是另一套设计，
不要在本单里顺手做。
