### F1-1 · 用例导入 / 导出

**做什么**

- 导出：把当前项目（或勾选的）用例导出成 **JSON**（本平台自有格式，可原样导回）和 **Excel**
  （人读友好，产品/测试评审用）。
- 导入：JSON 原样导回；**Postman Collection v2.1** 的请求转成接口用例（不需要 100% 还原，
  转 `method/url/headers/body` + 一条 `status_code` 断言即可）；冲突策略**默认新建**
  （不按名字覆盖——覆盖是不可逆操作，第一版不做）。
- 页面上放在用例列表页的工具栏，两个按钮：「导入」「导出」。导入用抽屉 + 预览 + 勾选，
  **预览里要能改名字**，别让用户导进来 200 条同名用例。

**复用现成代码（重点，别重写）**

旧的 PySide6 桌面版里有三份现成实现，逻辑与数据库解耦，剥掉 Qt 即可复用：

- `app/engine/json_exporter.py`（8.7KB）
- `app/engine/excel_exporter.py`（17KB）
- `app/engine/script_generator.py`（22KB，pytest 脚本导出，可留到 F3-3 用）

**涉及改动**

- 后端新增 `api/import_export.py`（路由）→ `main.py` 挂 `dependencies=guard`（F-C / C4）
- 新增 `services/case_exporter.py` / `services/case_importer.py`（纯函数，入参出参都是 dict，
  **不碰 DB**，照 `api_executor` 的写法）
- 导出用 `StreamingResponse` + `Content-Disposition`，文件名带项目名与时间戳
- 导入用 `UploadFile`，上限复用 `settings.dataset_max_bytes` 的思路（新增 `import_max_bytes`）
- 前端 `api/case.js` 加 `exportCases` / `importCases`；列表页加按钮 + `el-drawer` 预览

**验收**

- 导出一份 JSON → 删掉用例 → 导回来 → 字段逐一相等（写测试对比 dict）
- 导出一个 Postman collection（手写一份 3 请求的最小样例放 `backend/tests/fixtures/`）→

- `verify_all.py` 新增一段：导出 → 断言条数 → 导入 → 断言条数翻倍 → 清理

### F1-4 · 断言扩展

**现状证据**：`assertion_engine.evaluate()` 只实现 `status_code` / `response_time` / `response_body`
三类，`operator` 只有 `eq/ne/contains/regex/lt/gt`。

**新增（按顺序做，前三个最常用）**

| 断言类型 | target | operator | 说明 |
|---|---|---|---|
| `response_header` | 响应头名 | `eq` / `ne` / `contains` / `regex` | 查 `Content-Type`、`X-Request-Id` 这类 |
| `json_schema` | 空 | — | 期望值是 JSON Schema 字符串，校验整个响应体结构 |
| `body_length` | JSONPath | `eq` / `gt` / `lt` | 数组/字符串长度，查分页条数、列表条数 |
| `body_type` | JSONPath | `eq` | 字段类型（`string`/`number`/`boolean`/`null`/`array`/`object`） |
| `response_time` 的 `le` / `ge` | 空 | `le` / `ge` | 现在只有严格 `lt`/`gt`，等于边界值必然误判 |

**必须同步三处（F-C1）**

1. `services/assertion_engine.py` — 执行分支
2. `services/ai_prompts.py` 的 `ASSERTION_RULES` — 把新增组合写进提示词，
   **每条都写清 operator 取值与 target 含义**，否则 AI 会自创组合
3. `components/ApiCaseForm.vue` 的 `ASSERTION_TYPES` / `OPERATORS` — 下拉枚举

`json_schema` 的实现**不要引新库**：`jsonschema` 不在 `requirements.txt` 里。
先用「精简校验器」：支持 `type` / `required` / `properties` 三层递归，够覆盖 90% 场景，
并在界面注明「只校验 type/required/properties」。**如果要完整实现，先来问要不要加依赖**。

**验收**

- 每种新断言各一组「通过 / 失败」测试（`tests/test_assertion_engine.py`）
- `response_header` 用靶子接口 `GET /api/perf-target/echo` 验 `content-type contains application/json`
- AI 生成一条含新断言的用例（提示词里已列出新组合）→ 存库 → 执行通过
- `verify_all.py` 新增每类断言至少 1 条

**不要做**：不要在 `evaluate()` 里 import 需要新增依赖的库；不要改已有三类断言的语义。

### F1-5 · 失败重试

**做什么**：用例上加 `retry_times`（0–3）和 `retry_interval_ms`（0–5000）。
**只对「执行错误」重试，不对「断言失败」重试** —— 断言失败是产品行为，重试只会把真问题藏起来，
而且会让一条用例的执行时长变成 N 倍。

**涉及改动**

- `models/testcase.py` 加两列 → 登记 `_ADDED_COLUMNS`（F-C3）
- `schemas/testcase.py` 的 Create / Update / Out / Brief 各加一处
- `services/api_executor.execute_case()`：把「发请求 + 断言」抽成内部函数，按
  `retry_times` 循环；`result` 里加 `attempts: int` 和 `retry_errors: [str]`，
  **执行中心要能看出「重试了 2 次才成功」**，否则用户会以为一次就过
- Web 执行**不支持重试**（浏览器重跑成本太高，还可能留下脏状态），界面上对 Web 用例隐藏该字段
- `ApiCaseForm.vue` 加两个数字输入

**验收**

- 指向一个会超时/连不上的地址（如 `http://127.0.0.1:1/`），设 `retry_times=2` →
  结果是 `error` 且 `attempts == 3`
- 断言失败（期望 200 实际 404）时 `attempts == 1`，证明**没重试**
- `verify_all.py` 新增一段：用靶子 `?status=500` 造错误，断言 `attempts` 符合预期

**不要做**：不要对断言失败重试；不要在 Web 用例上开这个口子。

### F2-1 · OpenAPI / Swagger 导入

> **决策已定（2026-10-22）**
> - **粒度**：一个 `path + method`（即一个 operation） → 一条用例。**不按 tag 分组** ——
>   同 tag 成批会让用户没法按接口单独启停
> - **导入后一律 `enabled=false`**：一次导入几百条，谁也不想它们被正在跑的计划顺手带上
> - **`tags`** 取自 `operation.tags`，直接写进用例的 `tags` 字段（F1-2 的标签筛选正好用上）
> - **`$ref` 只解一层**：解不动的参数保留 `${参数名}` 占位符，把原因放进返回的 `warnings`。
>   **不许递归展开 schema** —— `allOf/oneOf/anyOf` 是无底洞，展开出来也是没人能维护的巨型用例

**做什么**：粘贴 Swagger JSON / 上传文件 / 填 URL（URL 拉取要做 SSRF 防护：
只允许 http/https、禁止 `127.0.0.1`/`169.254.`/内网 10.x·172.16-31.x·192.168.x —— 
**除非**用户显式打开「允许内网地址」开关，因为很多人就是这么用自己的 swagger 的）。

**转换规则（写清楚，别让它自由发挥）**

- 每条 `path + method` → 一条接口用例
- `url` = `paths` 的 key（相对路径），环境里用 `base_url` 拼
- `headers` ← 全局 `securitySchemes` 与 `parameters(in: header)`
- `query` ← `parameters(in: query)` 的**默认值/示例值**（这是 `params_json` 真正派上用场的地方，
  依赖修复单 P0-5）
- `body_type=json` ← `requestBody` 的 example / schema 生成的骨架
- 断言：`status_code eq 200` 一条起步（`responses` 里有更精确的 code 就用它）
- 名字：`{summary}` 或 `{method} {path}`

**验收**

- 用你自己平台导出的 `openapi.json`（`/openapi.json` 就能拿到）当输入 → 导入后条数 = operation 数（path × method），且全部 `enabled=false`
- 非法 JSON / 缺 `paths` / 空 `paths` 三种错误都要有明确中文提示，不能 500
- `verify_all.py` 新增一段（用 `backend/tests/fixtures/openapi_min.json`）

### F2-2 · 前置 / 后置用例（Setup / Teardown）

**前置条件（已定）**：决策 D1 已拍板 —— `pre_script`/`post_script` 从 API 层**删掉**
（任务在修复单 P1-7）。**P1-7 没做完不要开本卡**，否则会同时存在两套"前置"概念，
用户和代码都会迷糊。

**设计（已采纳）**：不做「让用户写 Python」（可执行任意代码 = 平台变后门），
改做**用例引用**：

- `test_case.setup_case_id` / `teardown_case_id`（`ON DELETE SET NULL`）
- 执行一条用例前，先按顺序跑 setup 用例（**继承其提取到的变量**），失败则主用例标
  `skipped`（不是 `fail`——语义要能区分开，执行中心要显示「前置失败」）
- teardown **无论主用例结果如何都执行**，结果单独记在 `result_json.setup` / `.teardown` 里

**验收**：主用例依赖前置用例提取的 `${token}` → 不配前置时失败、配了前置时通过；
前置失败时主用例状态是 `skipped` 且原因可见；teardown 在主用例失败时仍然执行。

### F2-3 · 变量管理升级

**做什么**

1. **Secret 类型**：`variables_json` 里区分普通值 vs 密钥。建议格式
   `{"token": {"value": "xxx", "secret": true}}`，**读取时对 secret 值回显 `***`**，
   编辑时不回显原文（留空 = 不修改）。执行时用真值。
   > 注意这会让 `variables_json` 从「扁平 key→str」变成「可能嵌套」，**所有读它的地方都要兼容**：
   > `api_executor`、`web_executor`、`scenario_runner`、`perf_runner`、`dataset` 的行覆盖逻辑。
   > 建议加一个 `services/variables.py` 统一 normalize，别在六处各写一遍 if。
2. **作用域：定为 3 层，不新增层级**（决策 2026-10-22）。
   解析优先级（高 → 低）：**数据驱动行 > 运行时提取 > 环境级**。
   - 环境级 = 现有 `environment.variables_json`。它的模型注释写着「取代旧库的
     global_variables 表」，所以它**既是「环境」也是「全局」** —— 别再拆成两个名字，
     否则同一个值会有两个入口
   - **不加「项目级」**：要新建字段 + 新 UI + 改 5 处读取点，收益只是「少复制几个变量」；
     单机工具里多建一个环境就能覆盖
   - **不加「用例级」**：会让「这个 `${token}` 到底哪来的」从三选一变成四选一排查
   - 优先级必须写进 `variable_resolver.py` 的 docstring（它现在的实现就是
     「运行时 > 全局 > 原样保留」，方向对，只是没写清「全局 = 环境」）
3. 环境列表页增加「变量」编辑抽屉，支持 secret 标记与显隐切换。

**验收**：同一变量名在三层都定义 → 断言最终取到的是优先级最高的那个（写测试覆盖 3 层）；
secret 值在 `GET /environments/{id}` 响应里是 `***`，在执行请求头里是真值。

### F2-4 · 用例变更历史 + 两版 diff

**做什么**：`test_case_history` 表（`case_id` / `snapshot_json` / `changed_by` / `created_at`）。
每次 `PUT /cases/{id}` 落一条**改前快照**。详情页加「历史」抽屉，支持选两版做 diff。

- diff **只在后端算**（返回结构化 `[{field, before, after}]`），前端只负责渲染。
- `snapshot_json` 用 `models/testcase.py` 的 `TestCaseOut` 序列化，别自己拼。
- 历史表要**限制条数**（每用例保留最近 20 版），否则会和 `execution` 一样无限膨胀。

**验收**：改 3 次 → 历史 3 条 → 选第 1 版和第 3 版 → diff 正确列出 `url`、`assertions_json` 的变化。

---

### F2-5 · 两次执行结果 diff

**做什么**：`GET /executions/diff?left={id}&right={id}` 返回：
`status` 变化、`duration_ms` 差值、响应体结构化 diff（JSON 递归比较，输出
`[{path, left, right, kind}]`）、断言结果变化。前端并排两栏 + 高亮。

**注意**：响应体可能被截断（修复单 P1-4），diff 时要在结果里标 `truncated`，
**不要**让用户以为「那边没这个字段」，其实是截断了。

**验收**：同一条用例跑两次（靶子 `?delay_ms` 不同）→ diff 里 `json.delay_ms` 显示为 changed；
用两个完全相同的执行 → diff 为空且界面显示「无差异」。

### F2-6 · 缺陷增强

> **决策已定（2026-10-22）：不接 Jira / 禅道的双向同步。**
> 本地 `defect` 表是**唯一事实来源**，不做「以对方为准」的缓存态。只做两件轻的：
> ① 缺陷列表增加「导出 CSV」（列名做成映射表，换对方模板只改一处）；
> ② `defect` 表加 `external_url` 字段，人工贴一条对方系统的链接。
> 理由：双向同步要 OAuth / token 轮换 / 回调 / 冲突合并，4 天起步，写坏一次就是
> 往对方系统里灌脏数据 —— 而测试团队的真实动作就是「导出 CSV 贴进去」。

**做什么**：`defect` 表加 `assignee`（用户名或自由文本）/ 新增 `defect_comment` 表 /
新增 `defect_attachment` 表（存文件到 `data/attachments/{defect_id}/`，库里只存元信息）。
状态流转加校验：`已关闭 → 重新打开` 允许，`新建 → 已关闭` 需要填 `resolution`。

**验收**：上传一张图 → 详情里能看到；加两条评论按时间排序；非法状态跳转返回 400 且有中文说明。

### F3-1 ~ F3-4（平台化，开工前必须单独排期）

只给要点，不给详细步骤——这几项动辄影响部署形态，**盲目开工的返工成本远高于收益**。

| ID | 关键要点（必须先想清楚的坑） |
|---|---|
| **F3-1 定时执行** | 调度器必须**常驻进程内**，而压测的运行注册表也是进程内的 → 两者都要求**单 uvicorn worker**（`CLAUDE.md` 已写明）。错过补偿**已定 `skip`**：只把错过次数记进 `scheduled_job.last_missed_count` 并在页面提示，
**不自动补跑** —— 补跑等于在你没准备的时候对被测系统发一批请求。计划正在跑时再次触发 → 跳过并记录，不要排队。表：`scheduled_job`（plan_id / cron / enabled / last_run_at / next_run_at）。**不要引入 Celery**。 |
| **F3-2 通知** | 只在 `execution` 到达**终态**时发一次（不要每条用例发一次，会把群刷爆）。通知内容要用 `report_url` + 通过率 + 失败用例名列表。渠道**已定：通用 webhook（自定义 JSON 模板）+ 预置企微 / 钉钉两个模板，首版不做 SMTP**。凭据（webhook URL / 邮件密码）必须走 secret（F2-3），**不能明文存库**。发送失败只记日志，**绝不能让通知失败导致计划执行报错**。 |
| **F3-3 CI 集成** | **顺序已定：先 ① 后 ②** —— 没令牌 CI 根本触发不了，导出只是离线保底。两种做法：① `POST /api/ci/run-plan` + `X-CI-Token` 头（token 独立于 JWT，有作用域限制，可吊销）；② 导出 pytest 脚本（复用 `app/engine/script_generator.py`，22KB，逻辑已与 DB 解耦）。**先确认 CI 里能不能跑浏览器**——不能的话 ② 只导出接口用例，别承诺 Web。 |
| **F3-4 多用户权限** | 现状是 `role` 字段**全库零鉴权点**（已 grep 确认）。要做就是：`project_member` 表 + `require_admin` / `require_project_role` 依赖（照 `api/deps.py` 的写法）+ 用户管理页 + 审计日志表。**这是安全边界，不是功能**——做完之前不要对外宣传「支持多人协作」。 |

## 5. 不建议做（想清楚了，别浪费工期）

| 想法 | 为什么不建议 |
|---|---|
| **Web UI 压测** | 浏览器渲染成本远高于服务端请求，测出来的是 Chrome 的性能不是你的系统。`CLAUDE.md` 已明确写过这条边界。真要做，先做「前端性能指标采集」（Navigation Timing / LCP），那是另一个产品 |
| **分布式压测（多机）** | 现在 `perf_run_manager` 是进程内注册表、单 worker 前提。上多机等于重写调度层 + 结果聚合 + 时钟对齐。单机 50 并发对本机被测系统已经够用 |
| **拖拽式 Web 步骤编排** | 现有 31 种操作的列表式编排已经够用，拖拽只是好看。投入产出比极低 |
| **让用户在执行时写 Python 脚本** | 等于把平台变成 RCE 后门。要灵活就用「前置/后置用例引用」（F2-2） |
| **自研断言 DSL（YAML 那套）** | 现在表单式断言 + JSONPath 覆盖了绝大多数场景，DSL 的学习成本比收益高 |
| **接入 echarts / 图表库** | 前端规范只允许 Element Plus。趋势图用表格 + CSS 条形足够。真需要图表再单独讨论，别在某个功能卡里偷偷引入 |
