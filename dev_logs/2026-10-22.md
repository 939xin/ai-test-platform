## 关键取舍
- **不复用 `execution` 表**：语义、状态机、统计口径都不同，混用会污染执行中心
- **不存每条请求明细**：只存聚合指标、直方图、时间线与最多 10 条错误样本

- **不引入图表库**：直方图与折线用纯 CSS / SVG 自绘，符合「只用 Element Plus」约束
- **单进程单活跃压测**：取消与实时进度依赖进程内注册表，文档已写明单 worker 前提

## 踩坑
- 直方图桶内插值可能越过真实 `max`（例如 p90=64 > max=63.59）。已在 `_build_metrics`
  里把百分位夹回 `[min, max]`，验收断言 `min ≤ p50 ≤ … ≤ p99 ≤ max` 才恒成立
- 运行中 `metrics_json` 为空，前端一开始把 duration 模式显示成「1000 次」、
  指标卡全是「—」。已改为运行中读进度接口的实时数据，模式回退读 `perf_run.load_mode`
- 停止接口返回的状态会停留在 `running`：manager 用自己的 Session 写 `stopping`，

### 关键取舍与坑

- **标签用 `FIND_IN_SET`，不用 `LIKE`**：`LIKE '%smoke%'` 会把 `smoke2` 一起筛出来，
  而且不报错 —— 用户只会觉得「筛选结果多了一条」。查询侧还套了
  `REPLACE(tags,' ','')`，因为库里存在手工写的 `"smoke, 订单"`
- **保存侧归一化 vs 查询侧 REPLACE 是两条路**：归一化后新数据没有空格，
  所以「REPLACE 是否生效」只能靠**绕过接口直插脏数据**来验。验收段里用
  `SessionLocal()` 直插一条 `tags="f12, 订单"` 再筛，才真正钉住查询侧
- **axios 数组参数默认是 `tag[]=a`**：FastAPI 只认重复的同名参数，
  不指定 `paramsSerializer.indexes = null` 的话筛选会**静默失效**（接口收到的是 `tag[]`，
  FastAPI 直接忽略）。已实测两种序列化结果并写进 `api/case.js` 注释
- **批量操作整批成功或整批不动**：先查全再校验 —— 有任何一个 id 不存在就 404、
  跨项目就 400，不会出现「前 3 条改了、第 4 条没改」
- **克隆的三条硬约束**：`enabled=false`（防止被计划误跑）、`login_case=false`
  （防止跑一次就把项目登录态覆盖掉）、JSON 列深拷贝（改副本不影响原用例）
- **`case-tags` 返回裸数组**：它是下拉数据源，形状不是 `{items,total}`；
  验收里专门有一条断言钉住 `isinstance(list)`
- **勾选只在当前页**：批量条文案写成「已选 N 条（当前页）」，不做跨页勾选

- **delta 左侧为 0 返回 `null`**：0 → 5 的「增长 500%」比「—」更误导人
- **warning 复用同一条机制**：用例不同、环境不同各一句，拼成一条字符串，都不阻断
- **空串语义贯穿三层**：schema 不把 `""` 转 None、API 不把 None 写库、
  前端空值显示「未标注」而不是报错
