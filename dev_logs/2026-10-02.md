### 任务 3b：场景串联 ★

**做法**：整个场景**共用一个 `VariableResolver`**。每步跑完把 `extracted` 灌进 `set_extra_var()`，
下一步执行时把「全局变量 + 运行时变量」合并后当作环境变量传给 `execute_case`。

之所以不去改 `execute_case` 的签名（让它接受一个现成 resolver），是因为合并变量字典这一步不侵入：
`get_all_variables()` 返回的正是「运行时优先」的结果。少改一处引擎代码，就少一处回归风险。

**新增**（8 个文件）
- `services/scenario_runner.py` —— 串联执行循环；`fail_strategy=stop` 时剩余步骤记为 `skip`（不是消失），
  前端才能说明「为什么只跑了 2 步」
- `schemas/scenario.py` + `api/scenarios.py` —— 场景 CRUD（steps 整体替换，`step_order` 由后端按数组顺序重排）
  + `POST /scenarios/{id}/run`；**每个步骤都落一条 execution**，执行中心与测试报告里能回溯
- 前端 `api/scenario.js` + `ScenarioList.vue` + `ScenarioEditorDrawer.vue`（选用例 / 上下移 / 失败策略）
  + `RunScenarioDialog.vue`（步骤条 + 逐步查看请求/响应/断言）

## 任务 3b 踩的坑：URL 拼接顺序错了（引擎真 bug）

第一次跑场景验收，两项失败。看结果：

```
✅ 步骤 1 提取到变量   https://httpbin.org/get
❌ 串联生效：步骤 2 的 ${echo_url} 被解析成上一步的值   https://httpbin.org/https://httpbin.org/get
```

变量**确实被解析了**，但最终 URL 被拼成了 `https://httpbin.org/https://httpbin.org/get`。

根因在 `api_executor.build_request()`：

```python
raw_url = case["url"]                      # "${echo_url}" —— 字面量不以 http 开头
if raw_url.startswith(("http://", ...)):   # ← 判断在解析之前
    full_url = raw_url
else:
    full_url = f"{base_url}/{raw_url}"     # ← 被当成相对路径，加了 base_url 前缀
full_url = resolver.resolve(full_url)      # ← 解析发生在最后
```

**只有「URL 完全由 `${变量}` 组成」时才会暴露** —— 而这正是场景串联最典型的用法。
旧桌面版也有同样的写法，只是旧版没有场景串联，触发不到。

- 修复：**先解析变量，再判断要不要拼 base_url**
- 验收里那条断言正是为它写的，所以修完立刻转绿

> 又一次印证：**用例之间的传参链路，只有真的串起来跑一次才发现得了问题**。

# Day 5 · 测试计划

## 起点：这是个从零设计，不是修 bug

起因是用户问「为什么测试计划用不了」。查下来它压根没开发过 —— `PlanList.vue` 是个 11 行的占位页。

再往下翻：**`docs/requirements/功能需求规格.md` 里没有「测试计划」这个词**，旧 PySide6 桌面版也没有。
它是新平台建库时预留的一张空表（`test_plan` 0 行数据），没有任何需求来源。

数据库里两个悬空字段也印证了这点：`test_plan.schedule` 全项目没有一行代码用过，
`execution.plan_id` 外键从来没被写入过。这次一并把它们收尾了。

## 定位：计划 ≠ 场景

两者最容易做重，先划清界限：

| | 场景测试 | 测试计划 |
|---|---|---|
| 用例关系 | 有顺序、有依赖，上一步的变量传给下一步 | 互不依赖，各跑各的 |
| 失败处理 | 可配「中止 / 继续」 | 固定跑完全部，最后统计 |
| 环境 | 执行时临时选 | 计划里绑定，作为默认 |

场景是「串联」，计划是「批量」。

## 表结构：JSON 串换成关联表

原来的 `test_plan.case_ids_json` 存 JSON 数组，问题是**没有外键** ——
删掉一条用例后，计划里会留下一个永远跑不通的死 id，只能手动去改计划。

改成关联表 `test_plan_case`（仿 `scenario_step`），外键 CASCADE，删用例时关联自动清掉。
验收里专门测了这条。

表里 0 行数据，所以结构随便改：`case_ids_json` / `schedule` 两列删掉，加了 `description`。

> 坑：`execution` 表有外键指向 `test_plan`，直接 DROP 表会被 MySQL 拒绝（errno 3730）。
> 改用 `ALTER TABLE ... DROP COLUMN / ADD COLUMN`，不动表本身，外键不受影响。

## 顺手做的三个改名

计划要复用单条执行的逻辑，把 `executions.py` 里三个内部函数提升为公开的：

- `_case_to_dict` → `case_to_dict`
- `_env_to_dict` → `env_to_dict`
- `_execution_out` → `execution_out`

纯改名，零行为变化，改完重跑验收确认没碰坏执行链路。

## 两个刻意的设计

**一、计划不因单条用例自身的问题中止整批。**

单条执行 Web 用例时没配步骤会直接抛 400；但在计划里，这条记一个 `error` 继续跑下一条。
计划是批量场景，一条没配好不该让其余用例都跑不成。
跑完汇总：全 pass 记 pass，有 error 记 error，否则记 fail。

**二、用例选择没用 el-table 内置的 selection。**

表格在筛选重渲染时内置勾选会丢，改成自己维护一个 id 数组。
验收里专门验证：搜索到 0 行时，已选仍然是 2 条。

## 阶段二：Web 步骤补全 16 种操作 + 交互重做

### 先查清楚「不全」是不是真的

翻下来：新平台 `ACTION_LABELS` 与旧桌面版 `ACTION_TYPES` **逐字一致，都是 15 种** ——
所以不是迁移时丢的，是两版本来就只有这些。对照 Selenium IDE / Katalon 的常用集，
缺的都是硬伤，尤其两个：

- **下拉框选择** —— 原生 `<select>` 用 `click` 点不开选项，必须走 `Select` 类，此前做不了
- **弹窗处理** —— 原生 alert 会卡死整个会话，不处理必然超时

补完后 **15 → 31 种**，按导航 / 鼠标 / 表单 / 弹窗 / 等待 / 滚动 / 断言 / 其他分 8 组。

### 架构上的改动：字段规格由后端声明

以前「这个操作要不要输入框」是前端用 `NO_INPUT_ACTIONS` / `WAIT_ACTIONS` 两个 Set
判断的，而后端另有一套 `needs_locator` —— 同一类信息两处维护。这次换成后端
`ACTION_SPEC` 声明每个操作的分组与所需字段，`/api/web/status` 原样下发，前端照着渲染。
以后新增操作只要在规格里加一条。

字段落在四个槽位上：`locator`（元素定位）、`target_locator`（拖拽目标）、
`value` / `value2`（两个参数）、`wait`（秒数）。

### 踩的坑：弹窗操作形同虚设（真 bug）

联调时 `alert_accept` 一直报「等不到弹出框」，但**紧接着的断言又通过了** ——
说明弹窗根本没停留，JS 直接往下走了。

单写一个最小脚本验证：headless 和 headful 下 `switch_to.alert` 都能拿到弹窗，
说明弹窗是存在的。那问题就在我们自己身上：

**Selenium 4 默认 `unhandledPromptBehavior = "dismiss and notify"`** ——
只要弹窗开着时有任何命令发过来，它就把弹窗关掉。而 `_robust_click()` 点击后紧跟一段
「等 DOM 稳定」的 `execute_script`，正好撞上，于是弹窗被悄悄关掉，
轮到用户的 `alert_accept` 步骤时已经没有弹窗可点了。

改成 `options.set_capability("unhandledPromptBehavior", "ignore")` 后 43/43 全过。

> 断言也可能碰巧通过，看起来一切正常，只有用户配的弹窗步骤是死的。
