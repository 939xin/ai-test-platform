### 双向跳转怎么串的

执行详情「提缺陷」→ `/defects?open=<缺陷id>&project=<项目id>` → 缺陷页自动打开抽屉。
缺陷详情「查看执行」→ `/executions?open=<执行id>` → 执行中心自动打开抽屉。

项目 id 一起带走是必须的：光给缺陷 id，缺陷页不知道该查哪个项目。
两个页面都在打开抽屉后用 `router.replace` 把 `open` 清掉，
免得用户关掉抽屉再刷新又弹出来。

同样的 query 用法在 Day 6 的用例编辑页已经用过（`?project=29`），保持一致。

### 重复提交的处理

同一条执行只允许挂一条缺陷。第二次点「提缺陷」时后端返回 **409**，
`detail` 形如 `{"message": "该执行记录已提过缺陷 #4", "defect_id": 4}`，
前端据此提示并直接跳转到已有那条。避免同一条失败被反复点出一串重复缺陷。

## 踩的坑

### 统一报错只认字符串 detail —— 是个真 bug

`api/request.js` 的响应拦截写的是：

```js
const message = detail || error.message || '请求失败'
```

而 FastAPI 的 `detail` 有三种形态：

| 场景 | 形态 |
|---|---|
| 业务异常自己抛的 | 字符串，如 `"缺陷不存在"` |
| **422 参数校验** | **数组**，每项 `{ loc, msg }` |
| 需要带额外数据时（这次的 409） | 对象，`{ message, defect_id }` |

后两种塞进 `ElMessage.error()` 就是 `[object Object]`。422 那条是**本来就存在**的
隐患 —— 之前任何一个表单校验失败，前端弹的都是这串乱码，只是没人细看。
这次一并修掉：按三种形态统一压成一句可读文案。

# 第二轮 · 全站 JWT 校验（Day 8）

同一天的第二轮。从第一轮末尾的清单里挑，按优先级选了 **全站接口 JWT 校验** ——
它是 Day 3 就记下的欠账，而且是安全问题，优先级最高。

## 动手前先纠正了一个写在项目里的错误认知

`CHANGELOG` 和 `CLAUDE.md` 都把这件事记成「登录能签发、前端也带上了，但后端没有一处 `Depends`」，
听着像是补个依赖就完事。**实际不是。**

查了两件事：

| 查什么 | 结果 |
|---|---|
| `api/health.js` 里导出的 `login()` 有没有调用点 | 没有，一处都没有 |
| 全前端有多少处 `localStorage` | **1 处，而且是 `getItem`（读）—— `setItem` 一个都没有** |

再加上没有 `stores/` 目录、没有 `Login.vue`、路由里没有 `/login`，
结论是：**前端根本没有登录这条路**。所以只补后端校验的话，改完那一刻整个 UI 就打死了 ——
每个页面都会 401，而且用户没有任何办法登进来。

这条是这次改动从「1~2 个文件」变成「9 个文件」的真正原因。

## 后端（4 个文件）

**`api/deps.py`（新）** —— `get_current_user`。没带 token / 伪造 / 过期 / `sub` 对应用户已被删除，
四种情况统一 401 并带 `WWW-Authenticate: Bearer`。

第四种是刻意加的：光验签不够，用户被删掉后旧 token 在过期前仍然验得过。

用 `HTTPBearer(auto_error=False)` 而不是手解析 header —— 顺带让 `/docs` 上出现 Authorize 按钮，
调试接口时不用手搓 curl。

**`main.py`** —— 守卫**不挂在各个路由函数上**，而是 `include_router(..., dependencies=guard)`：

```python
guard = [Depends(get_current_user)]
app.include_router(cases.router, prefix="/api", tags=["cases"], dependencies=guard)
```

好处是 11 个路由模块**一行都不用改**，豁免清单也只在这一个文件里看得见。
代价是新增路由模块时得记得挂上，否则它默认是裸奔的 —— 这条已写进 `CLAUDE.md`。

**`api/reports.py`** —— 拆成 `router`（受保护）+ `public_router`（豁免）。

## 豁免清单是推出来的，不是拍的

四条豁免各有理由，其中报告那两条是**被迫的，不是偏好**：

| 路径 | 为什么豁免 |
|---|---|
| `/api/auth/login` | 还没登录，此时必然没有 token |
| `/api/health` | `start.bat` 和前端登录前就要探活 |
| `/api/demo/*` | Selenium 浏览器直接打开 |
| `/api/reports/{filename}`<br>`/api/reports/screenshots/{path}` | 浏览器 `window.open` / `<img src>` 直接导航 |

最后一条值得展开：报告 HTML 里的截图是**浏览器渲染报告时自己发出的请求**，
不是前端代码发的。所以任何前端写法都带不上 `Authorization` 头 —— 这是浏览器导航的固有限制，
不是代码写得好不好的问题。全前端只有 3 个地方是这种 URL（grep 确认过：
`ReportList.vue` 的 `window.open`、`ExecutionResult.vue` 的 `:href` 和 `<img :src>`），
正好就是这两条路由。

安全性上没有裸奔：这两条路由各自都有 `../` 越界防护（`_safe_report_path` /
`_safe_screenshot_path`），不依赖鉴权兜底。

## 前端（5 个文件）

**`api/session.js`（新，20 行）** —— 登录态存取单独一层。
多出这个文件的理由：`request.js`（401 时清登录态）和 `auth.js`（登录时写登录态）都要碰
localStorage，而 `request.js` 不能反过来 import `auth.js`，否则是 `auth ↔ request` 的循环引用，
axios 实例初始化时会拿到 `undefined`。不拆的话就得在两个文件里各写一份 key 字符串。

**`views/LoginView.vue`（新）** —— 在 `AppLayout` 之外，独立全屏。没登录的人不该看到侧栏菜单。
配色全部走设计令牌，组件只用 Element Plus。

**`router/index.js`** —— 双向守卫：没 token 进受保护页 → 踢回登录页并把原地址记进
`redirect`；已有 token 还去登录页 → 直接送进项目页（否则登录后点后退又回登录页）。
`redirect` 只接受 `/` 开头且非 `//` 开头的值，挡掉开放重定向。

**`components/AppLayout.vue`** —— 顶栏原来是个写死的「鑫」字头像，现在显示用户名 + 退出登录。

**`api/request.js`** —— 401 拦截。

## 踩的坑

### 1. 登录接口自己的 401 不能按「会话过期」处理

后端密码错返回的是 401，跟会话过期的状态码撞了。第一版没区分，
结果**在登录页输错密码，弹的是「登录状态已失效，请重新登录」**，用户完全摸不着头脑。

判据是请求 URL：`error.config.url` 里含 `/auth/login` 就跳过失效处理，走普通报错路径。

### 2. 会话过期的提示根本来不及渲染

第一版是 `ElMessage.warning()` 之后**立刻** `window.location.href = '/login'`。
实测：页面直接卸载，**那句提示一次都没出现过** —— 用户莫名其妙就落到登录页了。

改成跳转前留 800ms。这类问题只有真跑一遍浏览器才看得见，`npm run build` 是查不出来的。

### 3. 多个并发 401 会连着弹一串

一个页面往往好几个请求同时在飞，token 失效时会连着回来一串 401。
加了个 `expiredHandled` 标记，只提示一次、只跳一次。
登录成功后是整页刷新，模块重新加载，标记自然复位。

# 第三轮 · 列表分页（Day 9）

同一天的第三轮。待办清单第一条，也是唯一一条**有实际性能影响的** ——
用例上到几百条，列表页会先把全部记录拉回来再渲染。

## 动手前先弄清楚「到底哪些接口能分页」

项目文档里写的是「8 个列表接口」，实际数出来是 9 个。所以没照文档做，
而是把前端的每一个调用点都 grep 了一遍，看每个列表接口**被谁消费**：

| 接口 | 调用点 | 结论 |
|---|---|---|
| `/projects` | **8 处下拉**（项目选择器） | ❌ 不能分页 |
| `/environments` | **4 处下拉**（执行弹窗选环境） | ❌ 不能分页 |
| `/datasets` | **1 处下拉**（数据驱动选文件） | ❌ 不能分页 |
| `/cases` `/executions` `/defects` `/plans` `/scenarios` `/reports` | 各自的列表页 | ✅ 分页 |

前三行是这次的**关键判断**：它们同时是「下拉数据源」。分页会让选择器
**静默只显示头一页的选项** —— 用户不会看到报错，只会发现「我的环境呢」。
这种缺陷比列表卡更隐蔽，所以契约里明确把它们排除在外。

于是定下一条**不对称的契约**（已写进 `CLAUDE.md`）：

- 会长的 6 个列表接口 → `{ items, total }`
- 给下拉当数据源的 3 个 → 保持裸数组

不对称是有意的，不是没统一。`verify_all.py` 里专门加了 2 条断言
（「项目列表仍是裸数组」「环境列表仍是裸数组」）钉住它，免得日后有人「顺手统一一下」。

## 后端（8 个文件）

**`schemas/common.py`（新）** —— `Page[T]`，一个泛型信封。
`total` 是**满足筛选条件的全部条数**，与 `limit`/`offset` 无关，前端靠它算总页数。

**`api/pagination.py`（新）** —— `PageParams` 依赖 + `paginate()` 助手。
抽出来是为了让 6 个接口共享同一套默认值与校验，否则某天改上限时总有一个漏掉。

两个约定值得记：

- 用 `limit` / `offset` 而不是 `page` / `page_size` —— `executions` 接口本来就带 `limit`，
  不引入第二套风格
- `total` 必须**单独 count 一遍**（`select(func.count()).select_from(stmt.subquery())`），
  不能拿 `len(rows)` 顶替 —— 后者只是本页条数

**`api/executions.py`** —— 新增 `GET /executions/stats`（见下）。

**`api/reports.py`** —— 这个接口的数据来自**磁盘上的 HTML 文件**而不是数据库，
所以分页是内存切片，没走 `paginate()`。文件名就是它的标识，顺带补了个 `ReportInfo` 模型。

## 两个接口顺序 / 口径的坑

### 1. `/executions/stats` 必须声明在 `/executions/{execution_id}` 之前

FastAPI 按**声明顺序**匹配路由。写在后面的话，`stats` 会被当成执行 id 去解析成整数，
直接 422。代码里补了醒目注释。

### 2. 统计卡必须改走后端，否则分页后会「翻一页数字就变」

执行中心的四张卡原来是对**当前加载的那一页** reduce 出来的
（旧代码注释自己写着「统计只针对当前加载的这一页记录」）。分页一上，它的口径就崩了。

所以加了 `GET /executions/stats`，和列表接口**共用同一个筛选函数** `_execution_filters()` ——
两处要是各写一份，早晚出现「列表筛了、统计没筛」的口径不一致。

`failed` 取 `fail + error` 的合计，与那张卡的既有口径一致，不给前端留加法。

## 前端（14 个文件）

**`components/PagePagination.vue`（新）** —— 只包了一层 `el-pagination`。
存在的理由：6 个列表页各写一遍 layout、每页条数选项迟早会漂移。

两个设计决定：

- **不走 `v-model`，只发一个 `change({ page, pageSize })`**。因为改每页条数时
  **必须连带把页码重置回 1**，两件事得一起生效。拆成两个 `v-model`，父组件就得自己
  保证这个先后顺序，容易漏
- **`hide-on-single-page`**。不然 3 条数据的列表底下也会挂一条全禁用的分页栏，
  纯噪音 —— 加了这个，条目少的页面和没做分页时**长得一模一样**，改动面反而更小

各列表页统一了三种刷新语义：

| 触发 | 行为 |
|---|---|
| 改筛选 / 换项目 / 点查询 | 回第 1 页 |
| 翻页 / 改每页条数 | 按新页码查 |
| 刷新按钮、抽屉保存后 | 停在当前页 |

另外「共 N 条」一律改成读后端的 `total` —— 原来写的是 `list.length`，分页后就成了本页条数。

## 顺手修掉一个数据丢失隐患

`PlanEditorDrawer` 提交时原本是这样拼 payload 的：

```js
cases: cases.value.filter((c) => selectedIds.value.includes(c.id))
```

拿**已加载的**用例列表去过滤勾选集。用例列表一分页，选择器就只能加载前 200 条 ——
编辑一个用例更多的计划时，**已勾选但没加载进来的用例会被静默删掉**，用户毫不知情。

改成直接从 `selectedIds` 提交。两个选择器都显式传 `limit: 200`（后端上限），
并且超过时**在界面上明说**「共 N 条用例，选择器只列出前 200 条」——
悄悄少几条比慢更难查。

## 三个口径上的取舍

1. **执行中心的统计卡不跟状态筛选走**（只跟项目走）。四张卡在筛选条**上方**，
   语义是项目总览；而且按状态筛完之后「通过率」只可能是 0% 或 100%，那张卡就没意义了。
   列表口径**是**跟筛选走的。反过来只需多传一个参数
2. **报告页上面那张勾选表不分页**。它要**跨记录勾选**，表头「全选」在分页下
   只选得到当前页，用户会以为全选了 —— 这是个比列表卡更糟的陷阱。
   下面的「历史报告」表正常分页
3. **删除本页最后一条时自动退一页**，否则用户会停在一张空表上

## 验收

| 层级 | 结果 |
|---|---|
| 后端 | `verify_all.py` **148 → 162 项全过**（新增 14 项分页边界） |
| 前端构建 | `npm run build` 通过 |
| 浏览器 | 6 个列表页逐页翻过，**0 console 报错、0 失败请求** |

新增的 14 项里有几条是钉边界的：`limit=0` / `limit=201` / `offset=-1` → **422**；
`offset` 越界 → 空数组但 `total` 不变；筛选与分页叠加时 `total` 只算筛选后的。

浏览器实测的几个关键动作（临时造了 25 条数据，验完已清理）：

- 执行中心 43 条 / 3 页，**翻到第 3 页只剩 3 行，统计卡仍是 43 / 34 / 9 / 79.1%** ——
  这正是改之前会错的地方
- 在第 2 页改筛选条件 → **自动弹回第 1 页**
- 计划选择器列出**全部 28 条**用例，不是 20 条

## 同一轮里发现并修掉的另外两个 bug

### 1. 报告文件名只精确到秒，同一秒连生两份会静默覆盖

连发 20 次生成请求，20 次返回的是**同一个文件名**，磁盘上最终只剩 1 份。

改成 `_write_unique()`：撞名就往后加序号 `_2` `_3`。

关键是用 **`open(path, "x")` 独占创建**占坑，而不是先 `exists()` 再 `write_text()` ——
后者在并发时两个请求会双双回「没有」，然后后写的把先写的盖掉，序号等于白加。

补了 2 条回归断言。**代价是 `verify_all.py` 每轮会多产出 3 个报告文件**，
所以把它加进了本来就有的收尾清理（原先只清 `report_name` / `web_report_name`），
跑完 `reports/platform` 回到原样。

### 2. 列表页挂载时会重复请求一次

`watch(currentProjectId, ...)` 会在 `loadProjects()` 给 select **赋初值**时也触发一次，
叠上 `onMounted` 里那句显式查询，开局必然查两遍 —— 请求面板里能看到两条一模一样的。

改成 el-select 的 `@change`：**只有用户真的选了才发，程序赋值不发**。
报告页本来就是这么写的，现在 7 个页面跟它一致了（顺带发现**环境列表**也有同一个 bug，
不在原先说的 6 个里）。

实测每页从 2 条降到 1 条；切项目功能没坏（接口用例页切项目后 URL 仍正确变成
`?project=8`，说明 `syncProjectToQuery` 未受影响）。
